# Spike 05: egress proxy for `network_mode: internal`

**Question:** how does an agent in a container reach the model API, and nothing else (manifest §4)? Build a minimal allowlist proxy or reuse an existing one?

**Answer: build the minimal Go proxy** (about 130 lines, standard library only, 7.6 MB image). It passed every containment and allow/deny check, refuses names that resolve to private addresses (the off-the-shelf proxy tested did not), and logs structured decisions rig can surface. Tested on Docker Desktop 29.9.2 with real Claude Code 2.1.319 behind Zscaler TLS inspection. Probe: `spikes/egress/probe.sh [proxy-image]`. Code: `spikes/egress/goproxy/`, `spikes/egress/tinyproxy/`.

## 1. Network design (verified)
Two Docker networks per ticket:
- `rig-<ticket>` created with `--internal`: no route out, no external DNS. Agent, service, and dependency containers live here.
- `rig-<ticket>-egress`: a normal bridge network that **only the proxy** joins (`docker network connect` after creating it on the internal network).

Measured from an agent on the internal network only:
| Check | Result |
|---|---|
| `curl https://example.com` directly | unreachable |
| `curl http://1.1.1.1` (raw IP) | unreachable |
| DNS lookup of `example.com` | no answer (no DNS exfiltration path either) |
| Service-to-service by container name | works (internal network DNS) |

The proxy is the only way out. It never terminates TLS (CONNECT tunneling only), so it cannot read or alter traffic, and the agent's own TLS (including the corporate CA baked in per spike 04) is end to end.

## 2. Candidates

| | Go proxy (recommended) | tinyproxy | squid (not built) |
|---|---|---|---|
| Image size | **7.6 MB** (`scratch` + static binary) | 136 MB (Debian; the Alpine package failed to install on Docker Desktop with `apk: Permission denied`) | larger (not measured) |
| Allowlist by host, `*.suffix` wildcards | yes | yes (regex filter, default-deny) | yes (`dstdomain`) |
| Port restriction | yes (`ALLOW_PORTS`, default 443) | yes (`ConnectPort`) | yes |
| Plain HTTP refused | 403 | 400 | configurable |
| **Refuses allowlisted name resolving to a private/loopback address** | **yes (403)** | **no: tunnel established to a private container** | yes, via a `dst` ACL (untested) |
| Dials the vetted IP (DNS-rebinding safe) | yes | no | partial |
| Logs | JSON lines: `{ts, action, host, reason}` | plain text, host included on denials | access log |
| Config | env vars / flags, trivially generated by rig | generated config file + filter file | config language |
| Extra moving parts | none | entrypoint script to translate rig's list | highest |

Claude Code worked through both (it answered `Invalid API key` for a dummy key, which proves the full path). The deciding points are the private-address guard, the structured logs, and having no second runtime to ship.

## 3. Go proxy behavior (what the spike code does)
- Only `CONNECT host:port`. Anything else (plain HTTP) gets `403`.
- Host must match the allowlist (exact name or `*.suffix`); port must be in `ALLOW_PORTS`.
- Resolves the name itself and **refuses** if no resolved address is public (loopback, private, link-local, unspecified, multicast); then dials the vetted IP directly. `ALLOW_PRIVATE=1` exists for tests only.
- Splices bytes both ways; half-close handled.
- Logs one JSON line per decision (`allow` / `deny` + reason), so rig can show "agent tried to reach X".
- Config: `ALLOW_HOSTS` (comma list), `ALLOW_PORTS`, `LISTEN` (default `:3128`).

## 4. What Claude Code actually contacts
With `HTTPS_PROXY` set and only `api.anthropic.com` allowed, the proxy saw:
| Host | Purpose | Needed? |
|---|---|---|
| `api.anthropic.com:443` | the model API (about a dozen CONNECTs in one short run: retries and parallel connections) | **yes** |
| `downloads.claude.ai:443` | auto-update check | no; denied, Claude carried on. Set `DISABLE_AUTOUPDATER=1` to silence it. |
| `http-intake.logs.us5.datadoghq.com:443` | telemetry/logging | no; denied, Claude carried on. Set `DISABLE_TELEMETRY=1` and `DISABLE_ERROR_REPORTING=1` (also referenced: `sentry.io`, statsig). |

Other hostnames present in the binary: `claude.ai`, `platform.claude.com` (login/OAuth flows) and `mcp-proxy.anthropic.com`. **Unverified:** whether a `CLAUDE_CODE_OAUTH_TOKEN` session needs `claude.ai` or `platform.claude.com`; not testable without a login (spike 04, §7). If it does, they go in the default allowlist; the config shape below makes that a one-line change.

Without the proxy environment, the same Claude run produced no output in 40 s (it cannot connect), confirming containment.

## 5. Gotchas for the implementation
1. **Set proxy variables in both cases.** curl only honors lowercase `http_proxy`; many tools want uppercase `HTTPS_PROXY`. Set `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY`, `http_proxy`.
2. **`NO_PROXY` / `no_proxy` is required for in-network traffic.** Verified: with `no_proxy=egress-svc` a call to a sibling container goes direct (works); without it the call goes to the proxy and is refused. Set it to `localhost,127.0.0.1`, the proxy name, and every service and dependency name in the ticket.
3. **Real work needs more hosts.** `npm install`, `go get`, `pip install` at run time need their registries (for example `registry.npmjs.org`, `proxy.golang.org`, `sum.golang.org`, `pypi.org`, `files.pythonhosted.org`). Dependencies baked into the image at build time need none. Make the allowlist configurable per ticket and per service; keep the default to the model API only.
4. **The proxy's own network is the egress.** On Docker Desktop the egress goes through the VM and the host's network, so it passes through Zscaler too; this worked in the test.
5. **A wildcard allowlist widens risk.** The private-address guard limits what a hijacked or rebinding name can reach, but prefer exact hosts.
6. **Plain-HTTP and non-443 services are blocked by design.** Anything that needs them must be added explicitly (port allowlist is global per proxy).

## 6. Config shape (additive, nothing implemented)
- Global config: `egress.default_allow` (default `["api.anthropic.com"]`), `egress.default_ports` (default `[443]`).
- `ticket.yaml`: `egress.allow: [host, ...]` (ticket-wide) and `services[].egress.allow` (extra hosts for one service; the per-ticket proxy enforces the union). Only meaningful when `docker.network_mode: internal`.
- The harness adds `DISABLE_AUTOUPDATER=1`, `DISABLE_TELEMETRY=1`, `DISABLE_ERROR_REPORTING=1` to claude-code agents in `internal` mode.
- New event: `egress.denied` (`{host, port, reason}`), emitted by the daemon from the proxy's JSON log, so the dashboard can show blocked attempts (useful to discover a missing allowlist entry).

## 7. Shipping the proxy
The proxy must run in a container (the internal network has no route to the host). Options, in order of preference:
1. **Embed a prebuilt static Linux binary** (`linux/arm64` and `linux/amd64`, about 3 MB each) in the rig binary with `go:embed`; at start, write a tiny build context (`FROM scratch` + the binary) and `docker build` it once (cached by content hash, no network needed). Rig stays a single normal Go binary.
2. Build from source in a `golang` image on first use (4 s, needs the base image).
3. Publish an image (adds a registry dependency; avoid for v1).

Recommendation: option 1, with the proxy as `internal/egress` and a small `cmd/rig-egress` main used to build the embedded binaries by `task release`.

## 8. Decision
- Per-ticket pair of networks: internal (all containers) + egress (proxy only).
- The Go allowlist CONNECT proxy, config via env, embedded and built as in §7.
- Defaults and gotchas in §4–6 become task 42 requirements. Formats additions made (additive): network name `rig-<ticket>-egress`, event `egress.denied`. Manifest §4 updated.
