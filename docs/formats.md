# RIG Formats and Contracts

The exact shapes that every part of rig shares. `manifest.md` says *what* and *why*; this file says *exactly how*. If a task needs a shape not defined here, stop and ask the user, then add it here in the same branch.

**Change rules:** adding a field, method, event, or enum value is fine (additive). Renaming, removing, or changing the meaning of anything needs the user's approval. Readers must ignore unknown fields; writers must keep `schema_version`.

---

## 1. Conventions
- Timestamps: RFC 3339 UTC (`2026-11-05T14:03:00Z`). Durations in Go-style strings (`30s`, `5m`).
- JSON keys: `snake_case`. YAML keys: `snake_case`.
- Ticket id: `^[a-z0-9][a-z0-9-]{0,62}$`. Service/dependency name: `^[a-z][a-z0-9-]{0,30}$`. Names are unique within a ticket (services and dependencies share one namespace).
- All paths stored in files are absolute, except `ticket.yaml` service `path` (relative to the ticket dir).
- Every persisted JSON file has `"schema_version": 1` at the top level.

## 2. Filesystem locations
| What | Path | Override |
|---|---|---|
| rig home | `~/.rig` | `RIG_HOME` |
| global config | `~/.config/rig/config.json` | `RIG_CONFIG` |
| the fleet (named vessels) | `~/.config/rig/fleet.json`: `{"vessels": {"<name>": "<config path>"}}` | |
| tickets | `<rig home>/tickets/<id>/` | |
| daemon socket | `<rig home>/rigd.sock` | |
| daemon pid | `<rig home>/rigd.pid` | |
| daemon log | `<rig home>/rigd.log` | |
| runtime cache store | `<rig home>/store.json` | |

**A ticket on a vessel.** Where a command takes a ticket as its first argument (`start`, `stop`, `phase`, `rework`, `approve`, `gates`, `push`, `review`, `reviewer`, `journal`, `attach`, `msg`, `logs`, `tests`), and in `rig wait`, a ticket can be named with its vessel, `<vessel>/<ticket>` (`osmo/t14`): the command then uses that vessel. A vessel named with `-V` that is not the ticket's is a usage error; one from `$RIG_VESSEL` gives way. When a vessel was chosen by name, every rig command the CLI prints (hints, and the daemon's messages) names it (`rig -V osmo phase t14 push`). `rig wait` takes several tickets, on one vessel or several, and ends on the first that matches, naming it (`ticket` in `--json`); `--new` with `--phase-request` ignores a request made before the wait started. `rig fleet` has a SPEND column per vessel (`$12.34`: the sum of every ticket's `cost_usd`, done ones included; `$0.00` for a vessel with no tickets), and `rig fleet --json` carries `spend_usd` and `spend_month_usd` (the part from tickets whose `created_at` falls in the current local month) per vessel; a stopped daemon's vessel is read from its tickets' state files, and the fields are absent when they cannot be read; the TUI's vessel picker shows the same spend, and `this month` in the selected vessel's detail line. `rig fleet` shows where each vessel's tickets stand (`13 (2 need you · 1 running · 10 done)`: need you is an open phase request, drift, an error, a stopped review, or a passed review not yet landed). `rig watch` streams events (`rig events` still works); `rig watch <ticket>... [--since <seq>]` prints just those tickets' timeline entries as they are made, after replaying from `--since` when given (0 = all), and reconnects from the last entry it printed.

**Choosing a vessel.** A vessel (also: instance) is one config with its own `paths.home`, daemon, agents and record; several can live on one machine, and the registered ones are the fleet. A command uses the first of: `--config <file>`, `--vessel <name>` (`-V`), `$RIG_CONFIG`, `$RIG_VESSEL`, the default config. A name is one registered in `fleet.json` (`rig fleet add <name> <config>`; letters, digits, `-`, `_`), or `default` for the default config when that file exists. `--config` with `--vessel` is a usage error, and so is an unknown name (the error lists the known ones). `$RIG_HOME`, when set, still replaces the chosen config's `paths.home`. `rig fleet` and `rig list --all` look at every vessel without starting a daemon. Bare `rig` on a terminal: with several vessels and none chosen, a picker first (`F` in the TUI returns to it); `-t <ticket>` and `--tab <tab>` open a view directly, and `Y` copies the command for the view on screen.

**The machine layer.** The default config (`<home>/.config/rig/config.json`) is also the machine layer every vessel's config is read over, so Claude login profiles (`auth`), certificates (`docker.extra_ca_certs`) and other Docker settings are set once. A key the vessel sets wins; objects merge key by key (so `auth.profiles` from both are kept); a list or scalar the vessel sets replaces the machine's whole, lists are never appended; `paths.home` is never inherited (a vessel without one gets `<home>/.rig`). The layer is always that file, whatever `$RIG_CONFIG` says, and is skipped when the vessel is that file; a missing one is fine, a malformed one is an error naming it. `rig config show --resolved` (also `rig config --resolved`) prints `{"config": <merged config>, "sources": {"files": {"machine"?, "vessel"?}, "keys": {"<key path>": "vessel" | "machine" | "default"}}}`, a list being one key. `rig fleet`, `rig list --all` and the picker leave out `default` when its home holds no ticket (a directory with a `ticket.yaml` under `tickets/`); `--vessel default` still works.

### Ticket sources (`rig new --from type:ref`)
- `manual` needs nothing. `jira:PROJ-412` reads one issue with `GET <jira.base_url>/rest/api/2/issue/PROJ-412?fields=summary,description` and nothing else: rig never writes to Jira. The ticket id is the lowercased key (`proj-412`); the title is the issue summary; the description (Jira wiki markup) is converted to Markdown into `plan.md`; the issue URL goes into the plan. `source: {type: jira, key: PROJ-412}` is recorded in `ticket.yaml`.
- Config: `"jira": {"base_url": "https://acme.atlassian.net", "email": "me@acme.com"}`. With `email` the credential is an Atlassian Cloud API token sent with basic auth; without it, a Server/Data Center personal access token sent as a bearer token. The credential is the `JIRA_API_TOKEN` secret (Keychain, then `.env`), looked up per request and never written to the config, ticket files, logs or errors. `base_url` must be https (http only for this machine).
- Errors: unknown or invisible issue `not_found`; a malformed key or a missing `jira.base_url` `invalid`; a rejected credential, a missing secret or a Jira outage `unavailable`.

- `github:owner/repo#123` reads one issue with `GET <github.api_url>/repos/owner/repo/issues/123` (GET only). The ticket id is `owner-repo-123`; the title and Markdown body come as they are (into `plan.md`, with the issue URL). A pull request is rejected (`invalid`): tickets are seeded from issues. `github.api_url` defaults to `https://api.github.com` (GitHub Enterprise: `https://host/api/v3`; https only, except this machine). The credential is the optional `GITHUB_TOKEN` secret: without it the request is anonymous, which works for public repositories within GitHub's low anonymous rate limit; with it, private repositories work. Errors: unknown, deleted or invisible issue `not_found` (the message suggests `GITHUB_TOKEN` when anonymous); rate limit, rejected token, outage `unavailable`.

## 3. Ticket directory
```text
<rig home>/tickets/<id>/
├── ticket.yaml        # human-owned config
├── state.json         # rig-owned truth (phase, approvals, ports, ids)
├── plan.md            # human + agent
├── tasks.md           # agent; GitHub checkboxes `- [ ]` / `- [x]`, progress = counted boxes
├── manual-tests.md    # agent-written; see §10
├── pr.md              # agent-written from implement on: the pull request description, published as written (§4 `policy.push`)
├── contract.md        # multi-service tickets only; see §9
├── .rig-events/<svc>/ # events.log: state words, cost lines and journal records (§14) appended by a container agent's hooks (§7); read by the daemon
├── .rig-claude/<svc>/ # the agent's own Claude Code configuration (`CLAUDE_CONFIG_DIR`, §13): every container agent, and a host agent with a credential profile
├── .rig-agent-config/<svc>/ # rig-written copy of the agent configuration templates (`agent_config`, §13), rebuilt at every launch; mounted read-only at `/rig/agent-config` in a container
├── journal.jsonl      # rig-written journal of agent records, stamped by rig (§14); never mounted into a container
├── timeline.jsonl     # rig-written, append-only: every change to the ticket once, in order, numbered from 1 (§15); never mounted into a container
├── journal.offsets.json # rig-written: how far into each service's events.log has been journaled (§14)
├── review/            # the reviewer's own clone, made again from the reviewed service's commit every round (`review`, §4); removed at stop
├── messages.jsonl     # rig-written log of messages typed into agents (`rig msg`, and rig's own notices with from "rig"): {at, service, from, text, delivered, reason?}
└── <service path>/    # checkout (default `./<service name>`): isolated shared clone in container mode, git worktree in host mode
```
`state.json` and `journal.offsets.json` are the only files rig rewrites; it also appends to `messages.jsonl`, `journal.jsonl` and `timeline.jsonl`, and creates the stubs of `rig new`. Agents must never edit `state.json` or `ticket.yaml`. `store.json` is a rebuildable cache (see manifest §1, principle 4).

## 4. `ticket.yaml`
Shape per manifest §5, plus:
- `services[].base`: base branch for the checkout and diffs. Default: the repo's default branch (`origin/HEAD`, else `main`, else `master`).
- `services[].path`: default `./<name>`.
- `services[].policy.gates`: absent = inherit; `[]` = no gates.
- **The pull request description** (pr mode) is the ticket's `pr.md`, never `plan.md`: `rig new` writes a stub (an HTML comment saying what it is for; with several services, one `## <service>` heading each) and `rig start` writes it for a ticket that has none. The body is the description with HTML comments removed (with several services, that service's section) followed by rig's table of changed files. `rig push` refuses a service, before pushing anything, when its description is empty, or when it contains the tickets directory, the rig home, the user's home directory or `/rig/ticket` (the agents' view of the ticket directory).
- `policy.push.mode` (`none | push-branch | merge | pr`, per service, ticket or global) and `policy.push.merge_commit` (bool, same levels, an explicit `false` overrides a `true` above it; default false): merge mode only fast-forwards the base unless it is true, in which case a merge commit is pushed when the base moved on. `policy.push.github_user` (a GitHub login, same levels; default none): in `pr` mode, the gh account the pull request is opened as when gh is logged in to several. rig takes that account's token from `gh auth token --user <login>` and gives it as `GH_TOKEN` to its own gh calls only; it is never stored, logged, shown or given to an agent, and gh's active account is not switched. Without it gh's active account is used. A login gh has no token for refuses the push before anything is pushed; so does a repository the account cannot see (rig looks for an open pull request first).
- `secrets`: names only. Values that look like secrets in `env` (high-entropy or known token prefixes) are rejected.
- Known gate names: `plan_approval`, `review_approval`, `manual_test_signoff`.
- `auth`: name of an auth profile from the global config (`auth.profiles`); ticket-level, overridable per service (`services[].auth`). Profile types: `host_login` (host mode only), `oauth_token`, `api_key`, `auth_token`, `bedrock`, `vertex`, `foundry`. A profile lists secret *names* (and non-secret env such as region); values never appear in any rig file or API payload. `sandbox: container` with a `host_login` profile is a validation error.
- Global config also has `auth.default` (profile name) `docker.extra_ca_certs` (list of PEM file paths) and `docker.port_range` (`{min, max}`, default 41000-41999, within 1024-65535: where host ports for service containers are allocated), `docker.agent_base` (default `debian:bookworm-slim`: the image an agent runs on when its service has no Dockerfile; otherwise the service's own image) `secrets.keychain_service` (default `rig`: macOS Keychain generic passwords of this service, account = the secret's name; on Linux the Secret Service items with attributes service=this and account=the name, read with `secret-tool`, see docs/linux.md), `secrets.env_file` (an absolute `.env` path, `~` allowed; consulted after the Keychain) and `docker.claude_version` (default `latest`: what the agent image's Claude Code installer is asked for).
- `services[].files`: list of `{path, from}`. At every `rig start`, after the checkouts exist and before any agent launches, rig copies `from` (an absolute host path to a regular file, at most 1 MB) to `path` (relative, inside the checkout, not in `.git`, each path once) and makes git ignore it: nothing is added when git already ignores the path; otherwise an anchored `/path` line goes into the clone's `.git/info/exclude`, or for a worktree into the main repository's. Nothing on the way is followed: a link where the file goes is replaced, and a linked directory or excludes file is refused. Checked before anything is made: `from` must exist, and must not contain the value of any secret the service's agent is given (named in the error, never shown); a file is meant to reference a secret, like `${NODE_AUTH_TOKEN}` in an `.npmrc`.
- `agent_config`: list of absolute paths to directories of agent configuration templates, laid out like `~/.claude` (§13). Ticket-level, and per service as `services[].agent_config`, which replaces the ticket's for that service's agent; absent inherits (service, then ticket, then the global `defaults.agent_config`, `~` allowed there), and `[]` means none.
- `services[].model`: passed to that service's agent as `--model`; absent leaves the harness's default.
- `review`: a reviewer agent for one service, `{of?, agent_config?, model?, copy?, max_rounds?, budget_usd?, tester?}`. `of` is the service reviewed (default: the ticket's only service; required with several). `agent_config` and `model` are the reviewer's own, as for a service. `copy` lists paths the repository ignores (installed dependencies such as `node_modules`; relative, inside the checkout, not in `.git`) copied from the reviewed checkout into each round's copy, copy-on-write where the filesystem allows; a link at the source, or on the way into the copy, is refused. `max_rounds` defaults to 3; `budget_usd` (default none) caps what all the ticket's agents spend in one loop. No service of such a ticket may be named `review`, which is the reviewer's name in state, events and commands. The reviewer always runs in a container, on the reviewed service's toolchain.
  - **A tester** (`review.tester: {agent_config?, model?, brief?}`, absent by default; a ticket without it behaves exactly as without this paragraph): a second agent, neither the coder nor the reviewer, that uses the built product as a user would. `agent_config` (absolute paths) and `model` are its own, as the reviewer's; `brief` is an absolute path to a file whose text heads the tester's prompt in place of rig's default (use the product as a user, never edit code or git, report each step with what was done and seen and PASS or FAIL against the plan, list what cannot be checked here), read when the tester is launched. No service of such a ticket may be named `tester`, the tester's name in state, events and commands. In every round, after the reviewer's copy is made, rig makes the tester its own copy, `<ticket>/tester/`, of the same pinned commit (never the coder's working tree; `copy` applied as for the reviewer), and launches its agent (state service `tester`) in its own container, on the same toolchain as the reviewer's, in an image with tmux added (a layer over the agent image; other agents keep theirs). The round brief typed to it names the plan, the round, the copy's path in its container (`/work`) and the service's `build.dockerfile`, `start`, `test`, `healthcheck` and `internal_port` hints; its ticket files are mounted read-only. It journals `test.result` (§14) once per round. **The round ends** when both the reviewer's `verdict` and the tester's `test.result` are in, in either order, and passes only when the reviewer's findings leave nothing blocking or should-fix and the tester's findings do too and its outcome is `pass`: a tester's `fail` with no blocking or should-fix finding counts as one blocking finding `T0`. Its findings are numbered `T1..` in the order given, handed to the coder in the same message as the reviewer's, labelled `(tester)`, and answered with `review.reply` by id. A coder's `disagree` on a tester's `blocking` finding stops the loop for a person, as on the reviewer's. The tester's spend counts in the loop's `budget_usd` and in the ticket's cost. A tester that cannot be launched stops the loop as a reviewer does. A person's `--pass` or `--stop` applies as before; a `test.result` after it is rejected.
  - **A round** starts when the reviewed service's agent journals `review.ready` (§14) or a person runs `rig reviewer <id> --start`, only in `implement`, only with no uncommitted work, and not while a round runs. rig fetches the coder's branch into the main repository as the hidden ref `refs/rig/review/<ticket>` (as `Import` does), empties `<ticket>/review/`, clones the main repository into it and checks out that commit detached through the hardened runner, then does the `copy`. So every round is a writable copy pinned to one commit; nothing the reviewer does there reaches the coder, and nothing from the last round survives. Each round's brief also lists what people (not rig) told the coder during the ticket and the coder received (`messages.jsonl`, the last 30), so a decision given by message is not taken for a deviation. The reviewer's agent (state service `review`) is launched at the first round and later rounds are typed into it; its ticket files are mounted read-only.
  - **A round ends** with the reviewer's `verdict` record (with a tester, when its `test.result` is in too, see below). Its `review.result` records since the round started (the latest per `id`) decide: any `blocking` or `should-fix` finding goes to the coder as one message (status `fixing`); none leaves the review `passed`. Nits are passed on for judgement only.
  - **Stops:** before another round, the loop stops for a person (status `stopped`, the coder told) when the round cap is reached with findings open, the loop's spend reaches `budget_usd`, or the coder answered a `blocking` finding with `disagree`. An agent cannot restart a stopped loop; `rig reviewer <id> --start` starts a new loop. **A question:** a coder's `review.reply` with status `question` while the loop is `fixing` stops it at once (by `rig`, the reason naming the finding and the question, `asked` set) without a round starting. The round it ended is not counted toward `max_rounds` (it keeps its number: `uncounted` counts such rounds, and the cap holds when `round - uncounted` reaches `max_rounds`), and `rig reviewer <id> --start` on such a stop continues the loop at the next round number, keeping its rounds, cost baseline and `uncounted`, instead of beginning a new one. A person's `--pass` or `--stop` clears `asked`.
  - **The gate:** a ticket with a `review` leaves `implement` forward only once its review has `passed`, by the reviewer or by a person (`rig reviewer <id> --pass --reason "..."`); otherwise the move is refused as `blocked`. A pass belongs to one commit: the reviewer's pass is bound to the round's commit (`review.commit`), a person's pass to the service's branch tip when it is given. While the review is `passed`, leaving `implement` and `rig push` require the branch tip to be that commit, and are refused otherwise (`the review passed <sha>, but the branch is now at <sha>: journal review.ready for a round on the new work (or rig reviewer <id> --start)`); `review.ready` then starts another round of the same loop, and a new pass lets the ticket go. A pass with no recorded commit (tickets from before this rule) is not checked. A move back to `implement` clears the review, so work sent back is reviewed again in a new loop. Checked when the ticket starts, before anything is made: each path must be an existing directory, and the agent must have its own configuration (every container agent; a host agent only with a credential profile).
- `egress.allow`: extra hostnames reachable through the egress proxy when `docker.network_mode: internal` (ticket-wide, and per service as `services[].egress.allow`; the ticket's proxy enforces the union). Global config: `egress.default_allow` (default `["api.anthropic.com"]`) and `egress.default_ports` (default `[443]`). Hostnames are exact or `*.suffix`.
- Unknown keys are errors naming the key and line.

## 5. `state.json`
```json
{
  "schema_version": 1,
  "ticket_id": "ticket-412",
  "phase": "plan",
  "approvals": [
    {"gate": "plan_approval", "service": "", "by": "human", "at": "2026-11-05T14:03:00Z"}
  ],
  "transitions": [
    {"from": "plan", "to": "implement", "by": "human", "reason": "", "at": "2026-11-05T14:05:00Z"}
  ],
  "services": {
    "backend": {
      "status": "pending",
      "checkout": {"kind": "clone", "path": "/abs/path"},
      "branch": "feat/x",
      "base": "main",
      "host_port": 0,
      "container_id": "",
      "agent": {"backend": "herdr", "pane_id": "", "state": "unknown", "container_id": "", "idle_since": "2026-11-05T14:00:00Z", "cost": {"usd": 0.42, "at": "2026-11-05T14:03:00Z"}},
      "push": {"status": "pending", "pr_url": "", "error": ""},
      "error": ""
    }
  },
  "dependencies": {"db": {"container_id": "", "status": "pending"}},
  "network": {"name": "", "id": ""},
  "egress_network": {"name": "", "id": ""},
  "contract": {"pending": false, "agreed_hash": "", "seen": [], "violation": ""},
  "manual_tests": {"steps": {}, "signed_off": false},
  "created_at": "2026-11-05T14:00:00Z",
  "updated_at": "2026-11-05T14:05:00Z"
}
```
- `approvals[].service` empty = applies to every service that requires the gate.
- `transitions[].by`: `human`, `agent:<service>`, or `rig` (the return after a sync, `sync_return` below). `reason` required for backward moves.
- `services[].status`: `pending | provisioned | running | stopped | error`.
- `agent.state` / `AgentState`: `working | blocked | idle | unknown | exited`. `services.<name>.agent.idle_since` (optional) is when the agent last became `idle`, absent in any other state; the review summary's `stalled` reads it, and each `services[]` entry of a ticket summary carries it as `idle_since` (RFC 3339) while the agent is `idle`.
- `push.status`: `pending | done | failed`. `push.files`, `push.added`, `push.deleted`: the size of the change pushed, measured just before the push (the checkout is gone later).
- `contract.pending` is true while some proposal is open; `agreed_hash` is the hash of the agreed section as rig last knew it to be right (set from the template when the ticket is created; follows edits freely during the `plan` phase); `seen` lists the proposal ids already announced; `resolved` lists proposals resolved through rig (their `contract.resolved` event was already published, so the file watcher skips them); `violation` is non-empty after the agreed section was edited directly once the plan phase is over, and stays until it is resolved.
- `egress_network` is present only in `network_mode: internal` (the proxy's outward network); absent otherwise.
- `review` (absent until the first round): `{status: reviewing|fixing|passed|stopped|awaiting_ready, round, commit?, base?, reason?, by?, cost_at_start, asked?, uncounted?, rounds: [{round, commit, at, verdict?, reviewer_done?, tester?: {outcome, at}}], at}`, the review loop (§4); `reviewer_done` and `tester` say which checkers of the round have answered (`tester` only with a `review.tester`). `commit` is the round's commit; a person's pass sets it to the service's branch tip when given, and a passed review binds leaving implement and push to it. `by` is `review` for a reviewer's pass, `rig` for a cap or a failed round, `human` for a person. Ticket summaries carry `review` `{status, round, reason?, at?, stale?}`; `at` is when the loop last changed (a round starting, or a pass, stop or other decision), so `rig wait --review <statuses> --new` can tell a verdict reached after the wait began from one already standing; `stale` is true when the status is `passed`, the pass recorded a commit, and the reviewed service's branch tip is not that commit (the check the gate makes), so tools do not offer the ticket for landing; a new round, or a pass with no recorded commit, is never stale. `stalled` `{service, since}` is set while the status is `reviewing` (a round is pinned) and a checker still owing its result (`review`, or `tester` when the ticket has one) has its agent `idle` since `since`, five minutes or more (`rig list` then shows `review stalled (<reviewer|tester> idle)` in place of the status); it clears when the result arrives or the agent works again. `rig list` shows `review <status> r<n>` after the phase (`review passed r<n> (new commits)` when stale), and `review waits for ready r<n>` for `awaiting_ready`. `awaiting_ready` means no round is running and none is pinned (`commit` empty, `round` kept): a sync that changed the reviewed branch leaves it there when the round it starts cannot start, and after a conflict; `review.ready` and `rig reviewer <id> --start` start a new loop's round 1 on the branch tip from it. `asked` (true) and `uncounted` (rounds that ended in a question stop) are described in §4. A state read with `reviewing`, no `commit` and no round being started by this rig process (it restarted, or the round was lost) is read as `awaiting_ready`. When its last round never pinned a commit (a lost round), `review.ready` or `--start` counts that round again in the same loop (round cap and budget are kept); after a sync every round had a commit, so it starts a new loop at round 1.
- `phase_request` (absent when none): `{to, service, reason?, at}` (ticket summaries carry `at` too), an agent's open request to move the ticket, made through its journal (§14). It never moves the phase or approves a gate; any phase move clears it. Ticket summaries carry it as `phase_request` `{to, service, reason?}`; `rig list` shows `(<service> asks for <phase>)` after the phase, and the TUI a `REQUEST <phase> (<service>)` marker, ranked just above APPROVE.
- `sync_return` (absent when none): a phase name, `test` or `review`; set when a sync moved a ticket with a `review` back from that phase to `implement`. When a round passes on the merged work rig moves the ticket forward to it, one step at a time through each phase in between (`transitions[].by` is `rig`, the reason `review passed on the merged work`), and clears it. rig checks and grants no gate for these moves, so the approvals the sync invalidated stay so and the gate still needs a person. Any other phase move clears it; a person's `--pass` does not use it.
- `question` (absent when none): `{service, text, at}`, an agent's open question to a person, made through its journal (§14). A person's message to that service that was delivered clears it; a phase move does not. Ticket summaries carry it as `question` `{service, text, at}`; `rig list` shows `(<service> asks you)` after the phase and `rig fleet` counts it as needing you.
- Writes are atomic (temp file + rename) and serialized per ticket.

## 6. Lifecycle rules
- Phases: `plan → implement → test → review → push → done`.
- Forward: exactly one step at a time. Backward: to any earlier phase, with a reason. `done` is terminal.
- Gate checks (a gate applies per service; a ticket moves only when every service that requires it has approved, or an approval with empty `service` exists):
  | Transition | Gate |
  |---|---|
  | plan → implement | `plan_approval` |
  | test → review | `manual_test_signoff` |
  | review → push | `review_approval` |
- Default policy gates: `[plan_approval, review_approval]`.
- For a ticket with more than one service, `plan_approval` is refused (`blocked`, with a detail saying what to write) while `contract.md` has nothing under `## Agreed` (only whitespace and guidance comments count as nothing); the plan → implement move is refused the same way if the contract was emptied after approval. Single-service tickets and tickets whose services do not require the plan gate are unaffected.
- Agents may *request* forward transitions; rig grants only if gates pass. Agents may not approve gates.

## 7. Naming and container topology
- Network: `rig-<ticket>` (created `--internal` when `network_mode: internal`); `rig-<ticket>-egress` (normal bridge, joined only by the egress proxy). Service container: `rig-<ticket>-<service>`. Agent container: `rig-<ticket>-<service>-agent`. Dependency: `rig-<ticket>-dep-<name>`. Egress proxy: `rig-<ticket>-proxy` (in `internal` mode it also publishes the services' host ports, which Docker cannot do for a container that is only on an internal network, and forwards them inward; env `ALLOW_HOSTS`, `ALLOW_PORTS`, `LISTEN`, `FORWARD=<port>=<service>:<port>,...`).
- Labels on every Docker object: `rig.ticket=<id>`, `rig.service=<name>` (when applicable), `rig.role=service|agent|dependency|proxy|network`.
- `rig.home=<rig home directory>` on every container, network and image a daemon creates. Several vessels (each with its own config, home directory and daemon) can share one Docker: a daemon lists only its own home's objects, and refuses to inspect, start, stop, remove, exec in or connect an object labelled with another home (naming that home). An object made before this label existed is found only by a lookup for its ticket, never by a scan, so reconcile never lists or removes it; remove such leftovers by hand. Ticket ids should still differ between vessels, because container and network names (`rig-<ticket>-...`) are shared by all of Docker.
- **Working topology (spike 04 confirms or amends):** per service, a *service container* runs the `start` command, and an *agent container* (toolchain image with the agent installed) runs the agent. Both bind-mount the same worktree and join the ticket network, so the agent can run tests and reach the service by name. Dependencies are siblings on the same network.
- In-network URL of a service: `http://<service>:<internal_port>`. Host URL: `http://localhost:<host_port>`.
- Git push credentials are never mounted into any container.
- **Repository access (decided in spike 04):** the checkout kind follows the sandbox. `sandbox: container` provisions an **isolated shared clone** (`git clone --shared <repo> <path>`, cloned from the repo's real, symlink-resolved path; branch created from `base`; the main repository's `.git/info/exclude` is copied in, so what it ignores locally stays ignored): the container mounts only that clone (rw, at `/work`) and the main repo's `.git/objects` **read-only at its real host path** (the clone's alternates point there). When the repo, or a store it borrows from, is reached through a symlink, the same store is also mounted read-only at that path, because a clone made by an older rig or an alternates entry written through the link names it. The main repo's refs, hooks, and config are never mounted, so an agent cannot touch other branches. `sandbox: host` provisions a real `git worktree`. `services[].checkout.kind` in `state.json` records which (`clone` or `worktree`).
- Work leaves a clone only through rig: `Import` fetches the clone's branch into the main repo (`git fetch <clone> branch:branch`); `rig stop` and `rig push` import first. Commits never exist solely in a clone that rig deleted.
- Host-side git against a clone is **untrusted-input safe**: rig runs those commands through a hardened runner that disables hooks, fsmonitor, external diff and textconv, pagers, and credential helpers, so a hook or config planted by the agent cannot run on the host.

## 8. Daemon API
Transport: unix socket, JSON lines (one JSON object per line, UTF-8, max 1 MiB per line).

Request: `{"v":1,"id":"<client-chosen>","method":"ticket.list","params":{}}`
Response: `{"v":1,"id":"<same>","ok":true,"result":{}}` or `{"v":1,"id":"<same>","ok":false,"error":{"code":"not_found","message":"..."}}`.
Streaming methods (`events.subscribe`, `logs.stream`) send many lines with the same `id`: `{"v":1,"id":"..","stream":{...}}`, ending with `{"v":1,"id":"..","ok":true,"end":true}`.
The daemon handles each request on a connection concurrently, so responses may arrive in a different order than the requests: clients match them by `id`. A client that wants a stream (`events.subscribe`, `logs.stream`) should open a dedicated connection for it; the stream ends when the client disconnects.
The first message on a connection must be `hello`: `{"method":"hello","params":{"client":"rig-cli","version":"x"}}`; the server replies with its protocol version, `server` (`rigd <version>`) and `version` (the daemon's build; an older daemon omits it and the client reads it from `server`). Mismatched major version is rejected. Every `rig` command that connects to the daemon prints one line on stderr, once per process, when the daemon's version and the CLI's differ (`rig: the daemon is version X but this rig is Y; run "rig daemon restart" ...`); stdout and `--json` are unchanged (with a vessel chosen the command names it: `rig -V <vessel> daemon restart`; `rig fleet` checks only the daemons it lists, and names each one's vessel), and a `dev` or unknown version on either side skips the check.

Error codes: `invalid`, `not_found`, `conflict`, `blocked` (gate/dirty/limit; `error.details` lists reasons), `unavailable` (Docker/terminal backend down), `not_running`, `internal`.

**Grouped views of the ticket list.** `rig list` has an `AGENT` column beside `TIME`: the summary's `agent_seconds` (`-` when 0), where TIME is the ticket's age, which overlaps other tickets and includes waiting. `rig list --group` prints the same table with a header row per phase in lifecycle order (plan, implement, test, review, push, done; a ticket with no readable phase under `unknown`, last; empty groups are left out) and, after a blank line, a footer row for the whole vessel. A header or footer is a row of the table, its cells under the columns they total: the first column holds `▾ <phase> (<count>)` (`▸` when folded; the footer is `all (<count>)`), so the ID column widens to the longest label; PHASE is blank; SERVICES shows the services' text when it is the same for every ticket in the group, else blank; COST is the sum of the tickets' `cost_usd` (blank when none reports one); TIME is the span from the earliest `created_at` to the latest `done_at`, or to now when any ticket in it is open; AGENT is the sum of `agent_seconds`; PORTS and TITLE show the value every ticket shares, else blank. Widths are measured over tickets, headers and footer together, so alignment holds with `--wide` and at any terminal width. Done tickets are one header row `▸ done (<count>)` unless `--all-done` (an error without `--group`); `--group` does not go with `--all`; `--json` is unchanged (grouping is a view). The TUI dashboard draws the same groups and rows from the same code (`ticketgroups`) in its own columns TICKET PHASE AGENTS PORTS COST TIME AGENT NEEDS TITLE: TIME and AGENT are the ticket's age and agent time as in `rig list`, AGENTS shows the lights when every ticket in the group has the same, NEEDS is blank on a header; when the terminal is too narrow to leave TITLE a share, TIME is dropped first, then AGENT, for every row alike. `done` starts folded; `z` folds or unfolds the group under the cursor (`enter` or `space` on a header too), `Z` folds all but the cursor's, `o` opens all; the cursor moves over headers and the tickets of open groups only; `g`/`G` go to the first/last visible ticket; actions (approve, push, ...) apply only with the cursor on a ticket. Fold state is kept per vessel for as long as the `rig` process runs, across the vessel picker.

New methods may be added by later tasks following the same envelope. Method payload types (`ticket.list`, `ticket.get`, `status`, and later ones) are defined in `internal/api`, whose JSON field names are the reference; this file fixes the envelope, error codes, method names, and events.

## 10. CLI conventions
- Every command that prints data supports `--json` (a global flag), printing exactly the API `result` payload.
- Human output to stdout, diagnostics and errors to stderr.
- Exit codes: `0` ok, `1` generic failure, `2` usage/invalid input, `3` blocked (gate, dirty checkout, limit), `4` daemon/backend unavailable, `5` not found.
- Destructive commands (`stop --force`, `reconcile --fix`) prompt unless `--yes`.
- Long text for a person at a terminal (`rig attach --read`) opens in `$PAGER`, else `less` at the end; `--no-pager`, `--json` or output that is not a terminal prints it instead.
- `rig review <id> [service] --files` lists the files each service has changed (the summary's `touched[]`, services with none say `no changes`) without building a diff; it cannot be combined with `--stat` or `--plain`, and with `--json` prints the `ticket.get` result (the service filter does not apply). `rig list` notes `overlaps <ticket>` on a ticket for each other ticket in the list, done ones excluded, that touches the same path in a service of the same name; computed by the client from the summaries' `touched[]`.
- A daemon that answers `unknown method` or `not implemented` for a method this client knows is older than the client: the client reports it as `unavailable` (exit 4), naming both versions, the method, and `rig daemon restart` as the fix, instead of the daemon's `invalid`.

## 11. `contract.md`
````markdown
# Contract: ticket-412

## Agreed
Free markdown. Machine-readable parts use fenced blocks tagged `endpoint` or `schema`:

```endpoint
POST /api/v1/dashboard
request: {"user_id": "string"}
response: {"widgets": ["string"]}
errors: 400 invalid_user
```

## Proposed changes
### P-backend-1 · from backend · open
**What:** add `locale` to the request.
**Why:** frontend needs localized widget names.

## Changelog
- 2026-11-05 P-backend-1 accepted by human: added `locale`.
````
- Proposal heading regex: `^### (P-[a-z][a-z0-9-]*-\d+) · from ([a-z][a-z0-9-]*) · (open|accepted|rejected)$`. The id embeds the proposing service, so agents never collide. The number is that service's next integer.
- Rejected proposals carry a `**Rejected:** <reason>` line.
- Agents append proposals only. Rig edits `## Agreed` and `## Changelog` on accept.
- Malformed proposals are reported, never silently dropped, and never hide valid ones. A proposal is malformed when its heading does not match, its id names a different service than its `from`, its id repeats, it lacks `**What:**` or `**Why:**`, or it is rejected without a `**Rejected:**` reason. The other proposals are still read. HTML comments (the template's guidance) are ignored everywhere, `###` lines inside code fences are text, and a field's value continues over following lines until the next marker.
- The fenced `endpoint` and `schema` blocks of `## Agreed` have a defined format, read by `rig contract check|export` (docs/contract-tests.md): an endpoint block is `METHOD /path` then `summary:`, `status:`, `request:`, `response:` and `errors:` fields; a schema block is a name then a JSON shape; shapes are JSON examples whose strings name types, `key?` is optional. Malformed blocks are reported with line numbers; blocks in proposals are ignored until accepted.
- `rig new` writes the template (guidance comments only, nothing agreed) for a ticket with two or more services; single-service tickets have no `contract.md`. "Nothing agreed" means the `## Agreed` section is empty apart from comments.

## 12. `manual-tests.md`
- Each step is a level-3 heading `### <step-id>: <title>` (id: `^[a-z0-9-]+$`, unique) followed by free markdown, usually with fenced shell blocks.
- Placeholders (rendered at read time): `{{<service>.url}}` (host URL), `{{<service>.port}}` (host port), `{{<service>.internal_url}}`, `{{<dependency>.host}}`, `{{ticket.id}}`. Unknown placeholders are errors listing every offender.
- Step completion is stored in `state.json` `manual_tests.steps[<step-id>]`, not in the file.
- A `### ` heading inside a fenced code block is text, not a step. Placeholders may appear anywhere (preamble, titles, bodies, code blocks), with optional spaces inside the braces (`{{ api.url }}`). `{{<service>.url}}` and `.port` need the service to be running (they are its host port); `.internal_url` needs `internal_port`. Anything else is reported, all offenders at once, including `{{...}}` text that is not a placeholder; the file is never rendered partially.

## 13. Harness prompt contract
- The prompt is the last argument, after `--` (Claude Code's `--add-dir` takes several values and would read the prompt as one more directory).
- **The agent's own configuration:** `CLAUDE_CONFIG_DIR` is `<ticket>/.rig-claude/<svc>/`, mounted read-write at `/rig/claude` in a container. A host agent gets one only with a credential profile (`oauth_token`, `api_key`, `auth_token`, cloud). `host_login`, or no profile, keeps the user's own configuration, because that is where the machine's login is. Before every launch rig merges into its `.claude.json` (0600, directory 0700): `hasCompletedOnboarding: true`, a `theme` if none is set, and `projects[<path>].hasTrustDialogAccepted: true` for exactly the agent's working directory and ticket directory. Those are the resolved real paths on the host, which must lie inside the tickets directory, and `/work` and `/rig/ticket` in a container. Every other key is kept. So a new agent starts at the input box with no first-run screens or trust prompts, and never loads the user's personal CLAUDE.md, skills or settings.
- **Agent configuration templates (`agent_config`, §4):** at every launch rig rebuilds `<ticket>/.rig-agent-config/<svc>/` from the templates, in order, a later template's file replacing an earlier one's. Only `CLAUDE.md`, `settings.json`, `agents/`, `skills/`, `commands/`, `output-styles/` and `hooks/` are copied; credentials, history and anything else stay out, and the templates themselves are never changed. Each of those entries in the agent's config directory becomes a link to the copy: to `/rig/agent-config/<entry>` in a container, where the copy is mounted read-only, and to the host copy for a host agent. A template's entry replaces one Claude Code wrote itself; a link to an entry the templates no longer have is removed. What an agent changes or adds through a link is gone at its next launch. A template is refused if it holds a link or any other non-regular file, if a file contains the value of a secret the agent is given (named, never shown), or if its `settings.json` sets `disableAllHooks` or `RIG_*` or `CLAUDE_CONFIG_DIR` under `env`. Rig's own hooks come in through `--settings`, and Claude Code runs the hooks of every settings source, so a template's hooks run next to rig's and cannot replace them. A hook script in a template is called as `"$CLAUDE_CONFIG_DIR/hooks/<script>"`, which works in both sandboxes.
- The launch prompt is assembled from: ticket title, current phase, `plan.md`, `tasks.md`, `contract.md` (multi-service only), and the rules for that phase. It never includes secret values.
- Rules every agent receives: edit only your service's checkout and, in the ticket directory (named as the agent sees it: `/rig/ticket` in a container), `plan.md`, `tasks.md`, and from `implement` on `manual-tests.md` and `pr.md` (the pull request description: published as written, so no local paths or links to private files; a reviewed coder updates it before each `review.ready`, and the reviewer treats a leak as blocking), and in a multi-service ticket proposals under `## Proposed changes`; never edit `state.json`, `ticket.yaml`, or `## Agreed`; request phase transitions, never assume them; write `manual-tests.md` with placeholders during/after `implement`. In `plan` the checkout stays unchanged. In `implement`, `test` and `review`: commit each change as soon as its tests pass without being asked, because rig imports, reviews and pushes commits only.
- **Phase notice:** after every move (forward or backward) rig types a notice into each service's running agent: `This ticket moved from <from> to <to>.` (`back to` for a backward move), ` Reason: <reason>.` when one was given, then the current phase and the same `## Rules`, `## This phase (<to>)` and, from `implement` on, `## manual-tests.md` sections a prompt for that phase has, with the ticket directory named as that agent sees it. It goes through the same injector as `rig msg` (`from: "rig"` in `messages.jsonl`). An agent that is blocked, still starting, or too slow to answer is tried again after 15s, the wait doubling up to 5 minutes, until the notice is delivered, a newer move replaces it, or the agent has exited.
- **Tester agents** (§4 `review.tester`): the prompt is the brief (the ticket's file or rig's default) followed by its fixed part: it uses the product, never commits, its working directory is a copy remade every round with tmux installed, it reports only through one `test.result` per round (§14), it has no phase to ask for and no gate to approve; then the coder's `plan.md`, `tasks.md` and `pr.md`. The round brief is typed to it like the reviewer's.
- **Reviewed and reviewer agents** (§4 `review`): in `implement` the reviewed service's agent is told that a reviewer checks its work and rig will not move the ticket on before the review passes, to leave `review.ready` instead of requesting a phase, and to answer each finding with `review.reply`. The reviewer gets its own prompt instead of a coder's: its job is to find what is wrong, not to make it work; its working directory is a copy remade every round that it may change but never commit; the coder's `plan.md` and `tasks.md` (read-only, the work log a claim to check); the record shapes of §14; and to wait for the first round, which is typed to it with the commit and the diff command. Later rounds' briefs list the earlier findings with the coder's answers.
- Every prompt has a `## Journal` section: how to leave a record (§14) by running the agent's own hook command with the record as its argument (`rig agent-event '<json>'` on the host, the events-file command in a container), and to use `"kind": "feedback"` whenever rig or the environment gets in the way.

## 14. Journal
A ticket's journal is what its agents chose to record: feedback about rig or their environment, results, anything an orchestrator wants kept. Agents write records; only rig writes `journal.jsonl`.

**What an agent writes** (one line, at most 64 KiB, UTF-8): `{"kind": "feedback", "text": "...", "data": {...}}`.
- `kind` (required): `^[a-z][a-z0-9_.-]{0,63}$`. `feedback` is for problems with rig or the environment; other kinds are free (`note`, `verdict`, `review.result`).
- `text` (optional): at most 16 KiB. `data` (optional): a JSON object; `null` means none.
- Any other field (`ticket`, `service`, `at`, `source`) is ignored: rig stamps those itself.

**How it reaches rig:**
- A container agent: a line of `.rig-events/<svc>/events.log` whose first non-space character is `{` is a record, never a state, even when it is malformed. The hook command appends its argument with `printf '%s\n'` so JSON escapes survive the container's `sh`.
- A host agent: `rig agent-event '<json>'`, which sends `agent.record`. A malformed record is dropped there, still with exit 0.

**`journal.jsonl`** (in the ticket directory, 0600, one JSON object per line, append-only): `{at, ticket, service, source, kind, text?, data?}`. `source` is `container`, `host`, or `rig`. rig writes a `record.rejected` record (source `rig`, `text` saying why, `data: {"line": <first 200 bytes>}`) for each malformed record a container agent wrote, so a mistake is visible instead of lost. When the record came from the `review` or `tester` service, rig also types it to that agent alone (never to the coder): the reason, the record's first 200 bytes, and to write the JSON to a file with a quoted heredoc, check it, and journal it again with `rig agent-event --file <path>`. `rig agent-event [--file <path>] <state|'<record json>'>` journals the one record in the file (at most 1 MiB) as it would the same text given as the argument, and is as silent on failure. Readers skip a damaged line.

**Exactly once:** the daemon journals the complete record lines of each events file from the offset saved in `journal.offsets.json` (`{"<service>": <byte offset>}`), then saves the new offset, so a restarted daemon neither loses nor repeats records (a crash between the two repeats them rather than losing them). A file shorter than its offset was truncated and is read from the start. Unlike states, records are not reduced to the last one when a file is first seen.

**Test records** (a ticket with a `review.tester`, §4): the tester leaves `test.result` once per round with `data: {outcome: pass|fail, findings: [{severity: blocking|should-fix|nit, text}]}` (text: a one-line summary). A second one in a round, one from another agent, one with no round running, or malformed adds a `record.rejected` record. The round ends when this and the reviewer's `verdict` are both in.

**Review records** (a ticket with a `review`, §4): the reviewed service's agent leaves `review.ready` (text: what is ready) and, per finding it was sent, `review.reply` with `data: {id, status: fixed|disagree|question, commit?, reason?}`; the reviewer leaves `review.result` per finding with `data: {id, severity: blocking|should-fix|nit, file?, line?, what, scenario?, fix?}` and closes a round with `verdict` (text `No blocking findings` or `Blocking findings: <n>`, `data: {round}`). A record from the wrong agent, a malformed one, a `verdict` with no round waiting or for another round, or a `review.ready` rig cannot act on adds a `record.rejected` record; a refused `review.ready` is also typed back to the agent with the reason. rig types the round brief, the findings, a pass and a stop into the agents through the phase notifier's delivery (retried while an agent is busy, logged in `messages.jsonl` from `rig`).

**Phase requests:** a record of kind `transition.request` with `data: {"to": "<phase>", "reason"?: "..."}`, from either sandbox, is journaled as usual and then recorded as the ticket's `phase_request` (§5). A missing or unknown `to`, or a request rig would refuse as asked (the phase the ticket is in, a skipped step forward, or, in a ticket with a `review`, the reviewed agent leaving `implement` before the review passes), adds a `record.rejected` record saying why and what to ask for instead, and the same is typed back to the agent. `rig wait <ticket> [--record <kind>[,<kind>]] [--phase-request] [--question] [--new] [--phase <p>] [--review <status>] [--timeout <d>]` subscribes to the tickets' timeline entries (no polling) and looks again at each one, until one holds (states already true count at once; records only if left after it started), prints it (`--json`: `{ticket, matched, record?, summary}`; `matched` is `record`, `phase_request`, `question`, `phase` or `review`), and exits 1 on timeout. `--record` takes several kinds, repeated or comma-separated (`--record note,question`), and ends on a record of any of them. `--question` ends when a watched ticket has an open question (the summary's `question`, open until a message to that service answers it); with `--new` only a question asked after the wait began counts (as `--new` does for `--phase-request`). With `--review`, `--new` ends only on a status the loop reached after the wait began (the summary's `review.at` not before the start): a later round's verdict, or a later decision on the same round; a pass already standing does not end it, and neither does an `awaiting_ready` read after a daemon restart (it keeps the loop's old `at`). Without `--new` nothing changes. `rig daemon restart [--force]` stops the vessel's daemon and starts it from this rig (a daemon not running is just started); it asks `daemon.busy` first and refuses, naming the tickets (`conflict`, exit 5), unless `--force`. The prompt's common rules name this record.

**Questions:** a record of kind `question` with `text` (what the person must decide; required, else `record.rejected`), from either sandbox, is journaled and then recorded as the ticket's open `question` (§5), replacing an older one. It is answered by a person's message (`rig msg`) to the same service that was delivered; a message to another service, one rig sends itself, or one that was refused does not answer it.

**Trust:** records are what an agent said, not facts rig checked. rig guarantees who wrote them and when, not that they are true, and does not scrub them: an agent that holds a secret can write it into a record.

## 15. Timeline
`timeline.jsonl` (in the ticket directory, 0600, one JSON object per line, append-only) is the record of everything that changed in a ticket, once and in order: `{seq, at, kind, by?, service?, data}`. Only the daemon writes it, through one writer that serializes appends, so `seq` counts 1, 2, 3, ... per ticket without gaps and a reader that has seen entry n asks for `since` n. `state.json`, `journal.jsonl` and `messages.jsonl` are unchanged; the timeline repeats what they hold only as far as needed to say what happened (a message's text, for one, stays in `messages.jsonl`). A ticket from before the timeline has no file and reads as empty; a torn last line (a crash in the middle of a write) is cut before the next append. A change is recorded after it was made, and a refused action records nothing. A timeline that cannot be written never fails the action.

`by` is `human`, `agent:<service>` (a reviewer is `agent:review`), or `rig`; `service` names the service the entry concerns, when there is one.

| `kind` | `data` | made when |
|---|---|---|
| `ticket.started` | `{}` | a start provisioned something new |
| `ticket.stopped` | `{}` | a stop took something down |
| `phase.moved` | `{from, to, reason?}` | the phase changed, by a person, an accepted agent request, a sync sending work back, `rig` returning the ticket to the phase a sync took it from once a round passed, or the last push |
| `gate.approved` | `{gate}` | an approval was newly given (`service` is set for a per-service one) |
| `phase.requested` | `{to, reason?}` | an agent's `transition.request` was recorded as the open request |
| `journal.recorded` | `{kind, text?}` | every record added to `journal.jsonl`, rig's own `record.rejected` included; `text` is cut to 200 bytes (the full text is in the journal) |
| `message.sent` | `{service, from, delivered}` | a message to an agent, delivered or not (the text is in `messages.jsonl`) |
| `review.round.started` | `{round, commit}` | a round's reviewer copy was made from `commit` |
| `review.round.closed` | `{round, verdict, blocking, should_fix, nit}` | the reviewer's verdict was taken; `verdict` is cut to 200 bytes; counts are of the round's findings |
| `test.result` | `{round, outcome, blocking, should_fix, nit}` | the tester's result was taken (`by` is `agent:tester`, `service` `tester`); counts are of its findings |
| `review.decided` | `{outcome, reason}` | the loop passed (`pass`, by the reviewer or a person) or stopped (`stop`, by rig at a cap or a failed round, or by a person) |
| `review.loop.ended` | `{rounds, status}` | the loop in `state.json` was dropped: a move back to implement, a sync that changed the reviewed service's branch, or a person starting a new loop over a stopped one. Its rounds stay in the timeline |
| `sync.done` | `{service, behind, merged?, conflicts?}` | a sync looked at a service |
| `push.done` | `{service, mode, pr_url?, files, added, deleted, error?}` | a push was tried for a service (a service already pushed is skipped, not recorded); `error` is set when it failed |
| `question.asked` | `{text}` | an agent's `question` record was recorded as the open question (`by` is `agent:<service>`; `text` is cut to 200 bytes) |
| `question.answered` | `{}` | a person's delivered message to the service that asked closed the open question (`by` is `human`) |
| `review.missed` | `{finding, lens?}` | `rig rework` sent a ticket back with a finding the review did not catch; `service` is the reviewed service or the ticket's only one, and empty on a several-service ticket with no `review`; `lens` is the kind of reviewer that should have caught it. `finding` is cut to 200 bytes (`phase.moved` has it whole) |

`rig stats` counts review rounds as the `review.round.started` entries of the whole timeline, so a loop that was reset still counts (never fewer than the rounds in `state.json`, which covers tickets older than the timeline). `rig timeline <ticket> [--since <seq>] [--json]` prints it.

## 16. `rig usage`

`rig usage <dir>... [--since <time>] [--json]` reads Claude Code transcripts that belong to no ticket (or any ticket's `.rig-claude/<service>` directory). It needs no daemon. Each `<dir>` is a Claude Code configuration directory: its transcripts are `<dir>/projects/<folder>/*.jsonl`, sub-agent files (`<folder>/<session>/subagents/*.jsonl`) included; a directory with none is an error naming it (exit 2), as is a `--since` that is neither RFC 3339 nor a date (`2026-11-01`, local midnight). A request counts once across all of a directory's files (message id and request id, as `rig stats` counts it), and with `--since` only entries stamped at or after the time count, the time before it too. A session is one transcript file.

Cost is worked out from tokens with the price table `internal/pricing/prices.yaml` (embedded; `taken` and `source` say where the rates come from; USD per million tokens as input, cache read and output, optional `tiers` by prompt size, cache writes at the input rate times `cache_write.five_minute` or `cache_write.one_hour`, split by `usage.cache_creation.ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`, all of `cache_creation_input_tokens` being 5 minute when the split is absent). It is not the harness-reported `total_cost_usd` that `rig stats` shows, so the two can differ. A model not in the table has its tokens counted and its name in `unpriced`, and is left out of `cost_usd`.

`--json`: `{since?, prices: {taken, source}, directories[], totals}`. A directory: `{dir, first?, last?, requests, tokens {input, cache_write, cache_read, output}, models[], cost_usd, unpriced[], agent_seconds, sessions[]}` where `agent_seconds` merges the timestamps of every file in the directory (the gap rule of `ticket.stats`: gaps of at most 15 minutes), and a session has the same fields with `file` (its path under the directory) instead of `dir` and `sessions`, and `cwds[]`: `{cwd, requests, cost_usd}` for each distinct `cwd` of its counted entries, in order of first appearance (a request counts under the `cwd` of the entry that counted it; entries with no `cwd` are under `""`; `--since` applies first), whose parts sum to the session's `requests` and `cost_usd` (absent when nothing was counted; directories and `totals` have none). The table has a `CWD` column: the first cwd, and `+N` when there are N more. `totals`: `requests`, `tokens`, `cost_usd`, `agent_seconds`, `unpriced[]` over all directories (`agent_seconds` summed per directory).
